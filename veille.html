Veille technologique

La sécurité des applications web en PHP/MySQL

Dernière mise à jour : 28 septembre 2026

1. Introduction

La sécurité web est aujourd'hui un sujet essentiel dans le développement d'applications. De nombreux sites utilisent des formulaires, des espaces de connexion, des bases de données, des sessions utilisateur ou encore des systèmes d'upload de fichiers. Tous ces éléments peuvent devenir des points d'entrée pour des attaques si le développeur ne met pas en place les protections nécessaires.

Une faille de sécurité peut avoir des conséquences importantes : vol de données, suppression ou modification d'informations, usurpation d'identité, indisponibilité du site, perte de confiance des utilisateurs ou encore impact financier pour une entreprise. C'est pour cela que la sécurité ne doit pas être ajoutée seulement à la fin d'un projet, mais pensée dès la conception.

Cette veille technologique est liée à mon parcours de développeur fullstack, notamment à mes projets en PHP/MySQL. J'ai déjà travaillé sur le traitement de formulaires, la validation des données côté serveur, la connexion à une base de données MySQL avec PDO et la sécurisation des données utilisateur. Ces notions sont directement liées aux failles les plus fréquentes dans les applications web.

L'objectif de cette veille est donc de comprendre les principales vulnérabilités web, de connaître les bonnes pratiques actuelles et d'identifier les sources fiables à suivre pour rester informé des nouvelles failles.

2. Le nouveau Top 10 OWASP (édition 2025)

L'OWASP a publié une nouvelle édition de son Top 10, qui remplace celle de 2021. Elle repose sur des données issues de plus de 2,8 millions d'applications et couvre 589 types de faiblesses (CWE), contre près de 400 dans l'édition précédente.

  1. A01 — Contrôle d'accès défaillant
  2. A02 — Mauvaise configuration de sécurité
  3. A03 — Défaillances de la chaîne d'approvisionnement logicielle
  4. A04 — Défaillances cryptographiques
  5. A05 — Injection
  6. A06 — Conception non sécurisée
  7. A07 — Défaillances d'authentification
  8. A08 — Défaillances d'intégrité des logiciels ou des données
  9. A09 — Défaillances de journalisation et d'alerte
  10. A10 — Mauvaise gestion des conditions exceptionnelles

Les principaux changements par rapport à 2021 :

  • A03 s'élargit : l'ancienne catégorie « composants vulnérables et obsolètes » couvre désormais toute la chaîne d'approvisionnement (dépendances, outils de développement, fournisseurs compromis). Elle a été classée n°1 par 50 % des personnes interrogées lors de l'enquête de la communauté OWASP.
  • A10 est une nouvelle catégorie : elle concerne les erreurs et exceptions mal gérées (messages d'erreur trop détaillés, application qui reste dans un état incohérent après une erreur).
  • La SSRF n'est plus une catégorie à part : elle est intégrée au contrôle d'accès défaillant (A01).
  • L'injection passe de la 3e à la 5e place, mais reste omniprésente : selon l'OWASP, 100 % des applications testées présentaient une forme d'injection. On compte plus de 14 000 CVE d'injection SQL et plus de 30 000 CVE de XSS.
  • A07 et A09 sont renommées : « Identification et authentification » devient « Authentification », et la journalisation met désormais l'accent sur l'alerte, pas seulement la surveillance.

3. Les vulnérabilités principales

a) Injection SQL (A05:2025)

L'injection SQL est une attaque qui consiste à envoyer du code SQL malveillant à travers une entrée utilisateur, par exemple dans un formulaire de connexion, une barre de recherche ou un paramètre d'URL.

Si une application construit directement une requête SQL avec les données saisies par l'utilisateur, un attaquant peut modifier la logique de la requête. Il peut par exemple contourner une connexion, lire des données confidentielles, modifier une base de données ou supprimer des informations.

En PHP, l'utilisation de PDO avec des requêtes préparées permet de limiter fortement ce risque. Le principe est de séparer la structure de la requête SQL et les valeurs envoyées par l'utilisateur. Les données ne sont donc plus interprétées comme du code SQL, mais comme de simples valeurs. C'est aussi la première recommandation de l'OWASP : garder les données séparées des commandes et des requêtes.

Exemple d'application concrète : dans un projet PHP/MySQL avec un formulaire de connexion, il ne faut pas insérer directement l'email et le mot de passe dans la requête SQL. Il faut utiliser une requête préparée avec des paramètres.

b) XSS — Cross-Site Scripting (A05:2025)

Le XSS est une vulnérabilité qui permet à un attaquant d'injecter du code JavaScript dans une page web consultée par d'autres utilisateurs. Cette faille apparaît souvent lorsqu'une application affiche des données saisies par un utilisateur sans les échapper correctement. Depuis 2021, l'OWASP la classe dans la même catégorie que l'injection SQL.

Par exemple, si un utilisateur peut publier un commentaire contenant du JavaScript et que ce commentaire est ensuite affiché tel quel sur le site, le navigateur des autres utilisateurs peut exécuter ce script.

Les conséquences peuvent être graves : vol de cookies, récupération de données sensibles, redirection vers un faux site, modification de l'affichage ou actions réalisées à la place de l'utilisateur.

Pour se protéger contre le XSS, il faut échapper les données avant de les afficher dans une page HTML, et éviter d'afficher directement du contenu utilisateur dans du JavaScript, des attributs HTML ou des URL sans traitement adapté.

c) CSRF — Cross-Site Request Forgery

Le CSRF est une attaque qui pousse un utilisateur connecté à effectuer une action sans s'en rendre compte. L'attaquant ne vole pas forcément le mot de passe, mais il profite du fait que l'utilisateur est déjà connecté sur un site.

Par exemple, si un utilisateur est connecté à son compte et qu'un attaquant lui fait cliquer sur un lien piégé, cela peut déclencher une action comme modifier une adresse email, supprimer un élément ou valider une opération.

Pour se protéger, il faut utiliser des jetons CSRF dans les formulaires sensibles. Un jeton CSRF est une valeur unique générée côté serveur, stockée en session et vérifiée lors de l'envoi du formulaire.

d) Faille d'upload de fichiers

L'upload de fichiers est une fonctionnalité très sensible. Une mauvaise gestion de l'upload peut permettre à un attaquant d'envoyer un fichier dangereux sur le serveur, par exemple un script PHP déguisé en image.

Pour sécuriser un upload, il faut vérifier plusieurs éléments :

  • l'extension du fichier
  • le type MIME
  • la taille maximale autorisée
  • le nom du fichier
  • le dossier de stockage
  • les droits d'exécution dans le dossier d'upload

Il est aussi préférable de renommer automatiquement les fichiers avec un nom unique, et le dossier d'upload ne doit pas permettre l'exécution de scripts.

e) Mauvaise gestion des sessions et des mots de passe (A07:2025)

Les erreurs fréquentes sont :

  • stocker les mots de passe en clair
  • utiliser un hash faible
  • ne pas régénérer l'identifiant de session après connexion
  • ne pas détruire correctement la session à la déconnexion
  • ne pas sécuriser les cookies de session
  • autoriser des mots de passe trop faibles

En PHP, les mots de passe doivent être stockés avec password_hash(), qui utilise des algorithmes adaptés comme bcrypt ou Argon2. Pour vérifier un mot de passe, il faut utiliser password_verify().

Il est aussi important de sécuriser les cookies avec des options comme HttpOnly, Secure et SameSite.

f) Composants obsolètes et chaîne d'approvisionnement (A03:2025)

Une application PHP/MySQL ne se limite pas à son propre code : elle dépend de la version de PHP, du serveur MySQL, du pilote de connexion et des bibliothèques installées avec Composer. Une version qui n'est plus maintenue ne reçoit plus de correctifs de sécurité, même si une faille grave est découverte.

Par exemple, PHP 8.1 est en fin de vie depuis le 31 décembre 2025. Un site qui tourne encore dessus reste exposé aux failles corrigées depuis dans les versions récentes.

L'OWASP recommande de tenir un inventaire à jour des dépendances (SBOM), de suivre les alertes CVE et NVD, et de mettre à jour la plateforme et les bibliothèques rapidement, en commençant par les failles les plus risquées.

g) Mauvaise gestion des erreurs (A10:2025)

Cette nouvelle catégorie concerne les situations où l'application gère mal une erreur. Un des scénarios décrits par l'OWASP est directement lié à PHP/MySQL : un message d'erreur de la base de données affiché à l'écran révèle la structure des tables, ce qui aide un attaquant à préparer une injection SQL.

En PHP, cela implique de :

  • désactiver display_errors en production et enregistrer les erreurs dans un fichier de logs
  • intercepter les exceptions PDO avec try / catch et afficher un message générique à l'utilisateur
  • utiliser des transactions (beginTransaction(), commit(), rollBack()) pour qu'une opération en plusieurs étapes, comme une commande, soit entièrement annulée en cas d'erreur

4. Bonnes pratiques actuelles

a) Utiliser les requêtes préparées avec PDO

Les requêtes préparées permettent de séparer la requête SQL des données utilisateur. Toutes les requêtes qui utilisent des données venant d'un formulaire, d'une URL ou d'une session doivent être préparées.

b) Hasher correctement les mots de passe

Un mot de passe ne doit jamais être stocké en clair. La bonne pratique est d'utiliser password_hash() avec bcrypt ou Argon2, conçus pour ralentir les attaques par force brute.

c) Valider et nettoyer les entrées utilisateur

Toutes les données envoyées par l'utilisateur doivent être validées côté serveur, même si une validation existe déjà côté navigateur. La sanitation consiste à nettoyer une donnée pour éviter qu'elle provoque un comportement dangereux, par exemple avant un affichage HTML.

d) Sécuriser la configuration MySQL

Il faut éviter d'utiliser le compte root de MySQL dans une application web et créer un utilisateur dédié avec uniquement les droits nécessaires. Il est aussi important de maintenir MySQL à jour et de faire des sauvegardes régulières.

e) Utiliser HTTPS et des headers de sécurité

HTTPS permet de chiffrer les échanges entre le navigateur et le serveur. En complément, certains headers HTTP améliorent la sécurité :

  • Content-Security-Policy : réduit les risques liés au XSS
  • Strict-Transport-Security : force l'utilisation de HTTPS
  • X-Frame-Options : limite le risque de clickjacking
  • X-Content-Type-Options : empêche certaines interprétations dangereuses
  • Referrer-Policy : contrôle les informations envoyées dans le referer

f) Utiliser une version de PHP maintenue

Au 28 septembre 2026, les versions de PHP encore maintenues sont :

  • PHP 8.5 (sortie le 20 novembre 2025) : correctifs de sécurité jusqu'au 31 décembre 2029
  • PHP 8.4 : correctifs de sécurité jusqu'au 31 décembre 2028
  • PHP 8.3 : correctifs de sécurité jusqu'au 31 décembre 2027
  • PHP 8.2 : uniquement les correctifs de sécurité, jusqu'au 31 décembre 2026

PHP 8.1 et toutes les versions plus anciennes ne sont plus maintenues. Pour un nouveau projet, il vaut mieux choisir PHP 8.4 ou 8.5, et installer chaque version corrective dès sa sortie.

g) Suivre le nouveau rythme des correctifs MySQL

Depuis mai 2026, Oracle ne publie plus ses correctifs de sécurité seulement tous les trois mois : des bulletins sortent désormais chaque mois, le troisième mardi. Il faut donc vérifier les mises à jour de MySQL tous les mois, et non plus une fois par trimestre.

5. Actualité récente

Événements marquants repérés pendant ma veille, du plus récent au plus ancien :

  • 24 septembre 2026 — PHP : le CERT-FR signale 10 vulnérabilités dans PHP (avis CERTFR-2026-AVI-1227). Il faut passer à PHP 8.2.34, 8.3.35, 8.4.26 ou 8.5.11. L'une d'elles (CVE-2025-1218) concerne mysqlnd, le pilote que PHP utilise pour se connecter à MySQL.
  • 19 août 2026 — MySQL : le CERT-FR relaie le bulletin mensuel d'Oracle d'août, qui corrige 34 vulnérabilités dans des produits MySQL, dont certaines permettent une exécution de code arbitraire à distance (avis CERTFR-2026-AVI-1049).
  • 31 juillet 2026 — PHP : correction d'une injection SQL dans l'extension PGSQL (CVE-2026-17543), détaillée dans l'étude de cas ci-dessous (avis CERTFR-2026-AVI-0952).
  • 17 juin 2026 — MySQL : nouvelles vulnérabilités dans MySQL Server, dont certaines permettent une exécution de code arbitraire à distance (avis CERTFR-2026-AVI-0765, bulletin Oracle du 16 juin 2026).
  • 7 mai 2026 — PHP : PHP 8.5.6 corrige notamment une faille XSS dans la page de statut de PHP-FPM (CVE-2026-6735) et une injection SQL dans le pilote PDO_Firebird (CVE-2025-14179).
  • Mai 2026 — Oracle : passage à des correctifs de sécurité mensuels.
  • 5 février 2026 — PortSwigger : publication du classement des 10 meilleures techniques de hacking web de 2025. On y trouve notamment une méthode pour extraire des données à travers les filtres de recherche des ORM, et une nouvelle technique de SSRF basée sur des boucles de redirection HTTP.
  • 31 décembre 2025 — PHP : fin de vie de PHP 8.1.
  • 20 novembre 2025 — PHP : sortie de PHP 8.5.
  • 15 avril 2025 — MySQL : publication de CVE-2025-21579, un déni de service sur MySQL Server 8.0, 8.4 et 9.x, exploitable par un utilisateur disposant déjà de privilèges élevés (score CVSS 4,9, gravité moyenne). C'était l'étude de cas de la première version de cette veille.

6. Étude de cas : CVE-2026-17543, une injection SQL dans PHP

Le 30 juillet 2026, PHP a publié des correctifs pour une faille intitulée « SQL injection via E'...' backslash breakout » dans l'extension PGSQL, celle qui permet de se connecter à PostgreSQL. Le CERT-FR l'a relayée le lendemain (avis CERTFR-2026-AVI-0952) en classant le risque comme « injection SQL ».

En PostgreSQL, une chaîne écrite sous la forme E'...' interprète l'antislash (\) comme un caractère d'échappement. D'après l'intitulé du correctif, un antislash mal traité permettait de « sortir » de la chaîne et donc d'ajouter du code SQL à la requête.

Versions concernées : PHP 8.2 avant 8.2.33, 8.3 avant 8.3.33, 8.4 avant 8.4.24 et 8.5 avant 8.5.9.

Ce cas est intéressant parce que la faille ne vient pas du code du développeur, mais du langage lui-même. Quelques mois plus tôt, une faille du même type avait été corrigée dans le pilote PDO_Firebird (CVE-2025-14179, injection SQL via des octets nuls dans les chaînes entre guillemets). Même une fonction d'échappement fournie par PHP peut donc contenir un bug.

Cette faille montre l'importance de plusieurs bonnes pratiques :

  • privilégier les requêtes préparées plutôt que l'échappement manuel des chaînes
  • maintenir PHP à jour, y compris pour les versions correctives
  • surveiller les avis du CERT-FR et le changelog de PHP
  • limiter les droits de l'utilisateur de la base de données, pour réduire les dégâts si une injection réussit malgré tout

7. Outils de veille et sources à surveiller

OWASP Top 10 — liste les risques les plus importants pour les applications web. Édition 2025 consultée le 28/09/2026.

NVD et CVE Details — permettent de suivre les vulnérabilités publiées officiellement (PHP, MySQL, Apache, Nginx, WordPress...) et leur score de gravité CVSS.

PHP.net Changelog et versions maintenues — pour suivre les correctifs de sécurité et savoir quelles versions sont encore supportées.

Bulletins de sécurité Oracle — correctifs de MySQL, publiés chaque mois depuis mai 2026.

PortSwigger Research, HackTricks et OffSec — expliquent les techniques d'attaque de manière pratique.

CERT-FR et ANSSI — sources françaises fiables publiant alertes et recommandations. Les avis du CERT-FR résument chaque faille en français et indiquent les versions à installer.

Réseaux sociaux et flux RSS — pour centraliser les alertes sans consulter chaque site manuellement. Le site du CERT-FR propose ses propres flux RSS.

8. Conclusion

Cette veille technologique m'a permis de mieux comprendre les risques principaux liés au développement web en PHP/MySQL. J'ai compris que les bonnes pratiques doivent être appliquées dès le début d'un projet : requêtes préparées, hashage des mots de passe, validation des données, sécurisation des uploads, gestion des erreurs, configuration MySQL et HTTPS.

La mise à jour de septembre 2026 montre que le sujet évolue vite : nouveau Top 10 OWASP, fin de vie de PHP 8.1, correctifs MySQL désormais mensuels, et des failles d'injection SQL découvertes dans PHP lui-même. Écrire du code sécurisé ne suffit pas : il faut aussi maintenir à jour tout ce sur quoi il repose.

Enfin, la veille ne doit pas être ponctuelle. Je continue à suivre l'OWASP, le CERT-FR, NVD, le changelog de PHP et les bulletins Oracle afin de rester à jour.
